# Как работаем

Нас двое (плюс агенты), сроки хакатонные. Правила короткие и направлены
на одно: **не тратить время на разбор конфликтов**.

## Главный принцип: одна задача — свои файлы

В каждой задаче есть раздел «Занимает файлы». Он не для красоты: пока
задача в работе, эти каталоги принадлежат тебе, а остальные не трогаешь.
Если задача требует влезть в чужой каталог — напиши в задаче, а не правь молча.

Раскладка спроектирована так, чтобы пересечений почти не было:

```
backend/api/auth/         задача 4
backend/api/catalog/      задача 5
```

## Порядок запуска

**Задача №1 (каркас и схема БД) блокирует всё остальное.** Её делает один
человек, мержим сразу, только потом разбираем параллельные.

Дальше можно брать что угодно из списка, но по приоритетам: сначала `P0`,
потом `P1`, `P2` — если останется время.

## Ветки и слияния

```bash
git switch -c feat/12-websocket     # feat/<номер задачи>-<коротко>
# ... работа ...
git pull --rebase origin main       # ОБЯЗАТЕЛЬНО перед push
git push -u origin feat/12-websocket
gh pr create --fill
```

* Ветка живёт **не дольше дня**. Долгая ветка — гарантированный конфликт.
* PR маленькие. Лучше три по 200 строк, чем один на 600.
* Мержим сквошем, чтобы история читалась.
* Защиту `main` не включаем — на хакатоне она мешает больше, чем помогает.
* Ревью необязательно, но перед мержем прогони `npm test` во фронтенде
  и тесты бэкенда.

## Три файла, где конфликты неизбежны

Их правила отдельные.

**Миграции.** Имя: `<timestamp>_<описание>.sql`, где timestamp —
**сплошное число без разделителей**: `20260921143000_response_entries.sql`.

Это требование sqlx, а не стиль: версией считается всё до первого `_`.
Если написать `20260921_1430_response_entries.sql`, версией станет
`20260921`, все миграции получат одинаковый номер и порядок применения
поедет. На этом уже наступили при написании каркаса.

Чужие миграции **никогда** не редактируем и не переименовываем — только
добавляем свою следующую. Так два человека физически не столкнутся.

**Регистрация роутов.** Добавляй свою строку **в конец** своей секции,
не переставляй соседние. Git сливает добавления в разные места без конфликта,
а перестановки — нет.

**Формы ответов сервера.** Лежат в `frontend/apps/react/src/shared/api/types.ts`
и списаны с обработчиков в `backend/src/api`. Меняешь форму ответа на сервере —
правь и там, одним коммитом. Фронтовой пакет `packages/domain` удалён
в задаче №18: второй реализации доменных правил в проекте быть не должно.

**Поля ответа не пропускаем.** `skip_serializing_if` на непустоту выглядит
экономией, а на деле заставляет каждого клиента сторожить обращение:
забытая проверка роняет весь экран. Пустой массив отдаём пустым массивом.

## Данные только с источником

Тренажёр учит людей работать с настоящей системой. Выдуманный признак —
это не «заглушка до лучших времён», а неверно обученный диспетчер.

**Никаких данных без источника.** Каждый признак, каждая формулировка
в опросной карте, каждое правило оповещения берётся либо со скриншота
боевой системы, либо из классификатора, либо из билетов. Источник
указывается в комментарии рядом и строкой в `PROVENANCE.md`.

Если источника нет — данные не добавляются. Лучше пустая карта, чем
правдоподобная выдумка: пустую видно сразу, выдумку — только при сверке.

На этом уже обожглись: опросные карты для ДТП и БПЛА были сочинены
при сборке фронтенда и лежали в одном массиве с настоящими. Сверка
с импортированным классификатором дала ноль совпадений из двенадцати.
Удалены, история в `PROVENANCE.md`.

## Чего не делаем

* Не форматируем чужой код «заодно» — это превращает diff в кашу.
* Не переименовываем файлы вместе с правками содержимого: сначала
  переименование отдельным коммитом, потом изменения.
* Не коммитим `node_modules`, `dist`, отчёты тестов — они в `.gitignore`.
* Не держим долгоживущих веток.

## Агентам

Задачи написаны так, чтобы агент мог взять их без дополнительного контекста:
в каждой есть цель, границы, занимаемые файлы, критерии приёмки и ссылка
на раздел `BACKEND.md`.

Если агент заводит новую задачу — тот же формат, обязательно с разделом
«Занимает файлы». Без него задачу брать нельзя: непонятно, с кем она
пересечётся.

## Прогон проверок идёт по своей базе

`TEST_DATABASE_URL` в `backend/.env` — отдельная база для тестов, и
трогать её руками не нужно. Но знать про неё стоит: пока её не было,
прогон работал там же, где стенд, и это было видно. В учётных записях
накапливались сотни курсантов вида `курсант1789977354456`, в переписке
учебных вызовов — реплики «проверка 1789977379959», а один из
тестовых импортов классификатора однажды стал активной версией.

Развернуть с нуля:

```bash
docker exec arm112-db psql -U arm112 -d postgres \
  -c "CREATE DATABASE arm112_test OWNER arm112;"

# Схему накатят миграции при первом прогоне, а классификатор — нет:
# он ставится отдельной командой
cd backend
DATABASE_URL=$TEST_DATABASE_URL cargo run --bin import_classifier -- \
  ../task/Классификатор*.xlsx "v046_24"
```

Браузерный прогон поднимает **свой** сервер на `:8081` и **свой**
клиент на `:5174`, оба смотрят в тестовую базу. Порты разведены
нарочно: с `reuseExistingServer` прогон подхватывал стенд, и смысл
отдельной базы пропадал.
