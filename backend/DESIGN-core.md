# Алгоритмическое ядро

Детерминированная часть бэкенда: классификация, оценка, статусы.
Нейросетей здесь нет ни одной — всё считается по классификатору
и правилам из памятки.

Это ядро определяет, что считается правильным. Всё остальное —
интерфейс к нему.

---

## 1. Конвейер классификации

```
ответы опросной карты
  questionId → выбранные варианты
        │
        │  ① сопоставление вариантов с признаками
        ▼
  (признак1, признак2, признак3)
        │
        │  ② поиск позиции классификатора
        ▼
  позиция: номер, итоговый тип, матрица служб
        │
        │  ③ вычисление условий оповещения
        ▼
  список служб + итоговый тип
```

### ① Сопоставление вариантов с признаками

Проблема: в опросной карте варианты сформулированы для человека
(«Улица», «Открытое пламя / Дым»), в классификаторе — свои
(«на улице», «открытое пламя»). Совпадают не все.

Решение — явная таблица, а не эвристика:

```sql
CREATE TABLE sign_mapping (
    type_id     text NOT NULL,           -- '101'
    question_id text NOT NULL,           -- 'where'
    option_value text NOT NULL,          -- 'Улица'
    sign_level  smallint NOT NULL,       -- 1, 2 или 3
    sign_text   text NOT NULL,           -- 'на улице'
    -- один вариант карты может давать несколько признаков:
    -- «Открытое пламя / Дым» это и 'открытое пламя', и 'дым'
    PRIMARY KEY (type_id, question_id, option_value, sign_text)
);
```

Для трёх карт со скриншотов таблица заполняется вручную и
просматривается человеком — там 36 вариантов. Для выведенных
из классификатора карт соответствие тождественное и заполняется
генератором.

**Вариантов без соответствия быть не должно.** Если вариант не
отображается ни в один признак, он помечается как информационный
(см. §1.4) — молча игнорировать нельзя.

### ② Поиск позиции

```
найти позицию P, где
    version_id = активная версия
    group_no   = группа выбранного типа происшествия
    sign1      = признак уровня 1 из ответов
    sign2      = признак уровня 2 (или NULL, если карта двухуровневая)
    sign3      = признак уровня 3 (или NULL)
```

**Комбинация может дать несколько позиций.** Пример: в вопросе
«Внутридомовые объекты» выбраны и «Квартира», и «Балкон» — это два
разных признака второго уровня, то есть две позиции.

Тогда:

* службы — **объединение** по всем найденным позициям;
* итоговый тип — от **самой тяжёлой** позиции.

Тяжесть закодирована в номере: у позиции `1050101` последняя цифра 1 —
открытое пламя, `1050102` — дым, `1050103` — запах гари. **Меньше цифра —
тяжелее происшествие.** Это не догадка: на сохранённой карточке ДДС
выбраны и «Открытое пламя / Дым», и «Запах гари», а класс вышел
«пожар: квартира», то есть позиция с единицей.

```
outcome = позиция с минимальным номером среди найденных
```

**Позиция не найдена** — это не ошибка сервера, а состояние карточки:
признаков недостаточно или они противоречивы. Возвращаем пустой список
служб и причину: какого уровня признака не хватило. Фронтенд показывает
это как «тип происшествия пока не определён», ровно как боевая система
не показывает список оповещения у незаполненной карточки.

### ③ Условия оповещения

Одна позиция оповещает службу по-разному в зависимости от дополнительных
признаков. Отсюда 104 колонки при 58 службах.

Виды условий в классификаторе:

| Вид | Примеры | Как вычисляется |
|---|---|---|
| **Предикат по карточке** | «угроза людям», «газификация», «перекрытие движение», «пострадавшие/погибшие», «тоннель», «НД — нет доступа» | по ответам опросной карты |
| **Базовый случай** | «признак не выбран», «признаки не выбраны» | когда ни один предикат группы не сработал |
| **Подразделение службы** | «Служба 101», «ОДС ПСЦ», «МГПСС» | не условие, а адресат внутри МЧС |
| **Служебное** | «МКП, Аналитика (Старый КРИМ)», «объект из перечня» | в MVP не трогаем |

Предикаты задаются таблицей, как и признаки:

```sql
CREATE TABLE condition_mapping (
    condition   text PRIMARY KEY,        -- 'угроза людям'
    type_id     text,                    -- NULL = для любого типа
    question_id text NOT NULL,           -- 'people-threat'
    match_value text NOT NULL            -- 'Да'
);
```

Алгоритм для каждой службы позиции:

```
подколонки службы = строки classifier_position_services
                    с этим service_id

если есть подколонка, чьё условие — сработавший предикат
    → берём её значение
иначе если есть подколонка «признак не выбран»
    → берём её
иначе
    → служба не оповещается
```

### 1.4 Значение в матрице: реагирование или копия

Ячейка матрицы содержит не флаг, а **значение**, и оно различает
два разных вида оповещения. Для позиции `1050101` (пожар: квартира):

| Значение | Служб | Что означает |
|---|---|---|
| `пожар: квартира`, `пожар`, `Пожар` | 8 | реальное реагирование, тип в системе службы |
| `карточка-112` | 19 | информационная копия карточки |
| `нет реагирования` | 1 | явное указание не реагировать |

Это объясняет цитату из памятки:

> Не все службы, которые должны оповещаться в соответствии с ЕКП,
> визуально отображаются в списке оповещения карточки. Службы, которые
> не реагируют, а, например, собирают информацию для дальнейшего
> анализа, не отображаются (для экономии места).

**Следствие для оценки.** Курсанта нельзя штрафовать за неоповещение
службы, которая получает только информационную копию, — он её и
не видит. Эталонный список для сравнения строится **только из служб
с типизированным значением**.

Дословные значения хранятся как есть и попадают в карточку: именно
их видит диспетчер в строке «Класс.». Обратите внимание на регистр —
`пожар` и `Пожар` в исходнике разные, нормализовать нельзя.

**Открытый вопрос.** Точное правило отображения по одному кадру
не выводится: на сохранённой карточке ДДС показан ЦЭМП, у которого
в матрице `карточка-112`. Либо правило сложнее, либо службу добавили
вручную. Занесено в `OPEN-QUESTIONS.md`.

### 1.5 Информационные признаки

Часть вариантов карты в классификации не участвует. «Дом
многоквартирный» в группе 1 не встречается вообще, а на сохранённой
карточке ДДС он показан — при классе «пожар: квартира», определённом
парой квартира + открытое пламя.

Такие признаки едут в службы как информация, но на список оповещения
не влияют. В `sign_mapping` они помечаются отдельно и в поиск позиции
не подаются.

**Оценка их тоже не штрафует** — по крайней мере до тех пор, пока
не будет ответа на вопрос №5 из `OPEN-QUESTIONS.md`.

## 2. Движок оценки

Сравнивает **три слоя**. Это единственное место, где мы делаем то,
чего не делает никто.

```
слой 1   скрытая истина сценария      что было на самом деле
слой 2   стенограмма разговора        что курсант выяснил
слой 3   карточка                     что курсант внёс
```

### Виды находок

| Вид | Условие |
|---|---|
| `ok` | совпало с эталоном **и** подтверждено разговором |
| `guessed` | совпало, но в стенограмме этого не было |
| `wrong` | значение не совпало |
| `missing` | поле не заполнено или служба не оповещена |
| `extra` | лишняя служба |

```
проверенные_поля  = ∪ unlocks(факты, которые курсант выяснил)
спрашиваемые_поля = ∪ unlocks(все скрытые факты сценария)

поле верное И ∈ спрашиваемые И ∉ проверенные  →  guessed
```

### Службы считаются, а не сверяются со списком

Эталонный список оповещения **не хранится в сценарии**, а вычисляется
тем же конвейером из §1 по эталонным ответам. Иначе при смене версии
классификатора сценарии начнут врать.

```
эталонные_службы = classify(эталонные_ответы_сценария)
фактические      = classify(ответы_курсанта) ∪ добавленные_вручную
пропущено        = эталонные ∖ фактические
лишние           = фактические ∖ эталонные
```

### Последствие вместо балла

Каждая находка несёт текст последствия: «служба не оповещена —
фактически не выехала», «силы уедут не на тот адрес». Балл считается,
но показывается вторым.

## 3. Машина статусов ДДС

Уже реализована во фронтовом домене, переносится как есть.

```
нет содержательных статусов  →  Принята | Не принята
последний «Не принята»       →  Принята
последний «Принята»          →  Начало реагирования, Прибытие,
                                Проведение работ, Работы завершены,
                                Отказ от выполнения работ
в цепочке хода работ         →  только статусы правее
терминальный                 →  пусто, карточка закрыта
```

Комментарий обязателен для «Не принята» и «Отказа от выполнения работ».
**Проверка на сервере обязательна** — фронт ограничивает выбор,
но запрос может прийти и мимо него.

Нормативы: подтверждение 30 секунд, завершение 48 часов.

## 4. Генератор ошибок для режима ДДС

Заказчик: диспетчер должен заметить, что оператор 112 ошибся.
Значит, карточка приходит **с намеренно внесённой ошибкой**.

Ошибки берутся не из головы, а из типов, которые классификатор
позволяет проверить:

| Тип ошибки | Как вносится | Как обнаруживается диспетчером |
|---|---|---|
| Неверный признак | подменить `sign2` на соседний из той же ветки | список служб не соответствует описанию |
| Пропущенная служба | убрать одну из автоподобранных | сверить с описанием происшествия |
| Лишняя служба | добавить непрофильную | то же |
| Ошибка в адресе | подменить корпус или подъезд | сверить с описательным адресом |
| Противоречие | признаки дают один тип, описание другой | чтение описания |

**Ограничение.** Если у диспетчера нет доступа к записи разговора
(вопрос №6 в `OPEN-QUESTIONS.md`), обнаружить можно только те ошибки,
которые видны **внутри самой карточки**: противоречие между описанием,
признаками и списком служб. Ошибки вида «оператор неверно расслышал»
без записи не ловятся, и подкладывать их нечестно.

Поэтому в MVP вносим только внутренне обнаружимые ошибки.

## 5. Порядок реализации

```
1. sign_mapping + condition_mapping — таблицы и наполнение
2. classify() — конвейер §1, с тестами на реальных позициях
3. POST /api/classifier/evaluate — обёртка над classify
4. grade() — движок §2
5. машина статусов — перенос из фронтового домена
6. генератор ошибок — §4, после ответа на вопрос о записи
```

Шаги 1–3 закрывают задачу #6 и разблокируют фронтенд.
Шаги 4–5 закрывают #9 и #10.

## 6. Что проверяем тестами

Не «работает ли код», а **совпадает ли с боевой системой**:

* пожар в квартире с открытым пламенем → «пожар: квартира», МЧС в списке;
* тот же плюс угроза людям → добавляется медицина;
* выбраны и пламя, и запах гари → побеждает пламя (проверено по кадру ДДС);
* БПЛА в регионе → «БВС Регион», ЦУКБ Минобороны;
* признаков не хватает → пустой список и внятная причина, а не ошибка;
* «Не принята» без комментария → отклоняется на сервере;
* одна и та же карточка даёт разный балл в зависимости от того,
  спросил курсант заявителя или нет.
