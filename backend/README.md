# Бэкенд тренажёра АРМ-112

Rust + axum + PostgreSQL. Полная спецификация — `../BACKEND.md`.

## Запуск с нуля

```bash
docker compose up -d          # PostgreSQL на 5432
cp .env.example .env
cargo run                     # миграции накатятся сами
```

Проверка:

```bash
curl http://127.0.0.1:8080/api/admin/health
# {"db":true,"uptime_sec":5,"ml_provider":"mock","version":"0.1.0"}
```

Нужен Rust stable. Если не стоит:

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
```

## Структура

```
src/
  main.rs       точка входа, сборка роутера
  config.rs     конфигурация из окружения
  error.rs      AppError → HTTP-коды из BACKEND.md §8.9
  state.rs      разделяемое состояние: пул БД, конфиг, адаптеры моделей
  api/          HTTP-хендлеры        ← по одному модулю на задачу
  domain/       классификатор, машина статусов, статус карточки,
                оценка, сравнение версий классификатора
  ingest/       импорт классификатора из XLSX
  jobs/         сторож нормативов и очередь задач
  reports/      отчёты по занятию и по группе, выгрузка в CSV
  ml/           адаптеры моделей + заглушки
  store/        подключение к БД и миграции
  ws/           канал класса: шина событий и эндпоинт /ws
  audit/        журнал действий
migrations/     SQL, накатываются при старте
```

## Фоновые задачи

Поднимаются вместе с сервером, отдельного процесса не нужно.

| Задача | Период | Что делает |
|---|---|---|
| `jobs::watchdog` | 5 с | пересчитывает статус сохранённых карточек |
| `jobs::worker` | постоянно | очередь `ml_jobs`: отчёты по группе, сводки |

**Сторож нормативов** не выполняет переходы, а вычисляет статус заново
из статусов служб (`domain/card_status.rs`). Поэтому он идемпотентен,
переживает перезапуск и сам исправляет карточку, если диспетчер
передумал. Нормативы из памятки ДДС: 30 секунд на подтверждение,
48 часов на завершение работ. Каждое изменение пишется в `audit_log`.

Запись идёт условным `UPDATE` по старому статусу: экземпляров сервера
может быть несколько, и без этого условия один переход попал бы
в аудит столько раз, сколько экземпляров успело его заметить.

**Очередь** — таблица `ml_jobs` с `FOR UPDATE SKIP LOCKED`, без брокера.
Туда уходит всё, что не должно ждать в HTTP-запросе: норматив ТЗ на
отчёт по группе — 30 секунд, эндпоинт отвечает `202` и номером задачи,
клиент опрашивает `GET /api/jobs/:id`.

## Описание API

```
GET /api/openapi.json     схема OpenAPI 3.1
GET /api/docs             Swagger UI
```

Схема собирается из самих обработчиков (`utoipa`), а не пишется
отдельным файлом: отдельная разошлась бы с кодом на первой правке и
стала бы хуже, чем её отсутствие — интегратор доверял бы описанию,
которое врёт. `tests/openapi.rs` читает маршруты прямо из исходников
роутеров и падает, если какой-то не описан или описан лишний.

Как встроить сервис в стороннюю систему — `INTEGRATION.md` в корне.

## Разграничение доступа

ТЗ распределяет функции между ролями довольно жёстко, и мы следуем
буквально:

| | Преподаватель | Администратор |
|---|---|---|
| Сценарии, задания, группы | да | — |
| Отчёты и аналитика по группе | да | да |
| Последствия смены версии классификатора | да | да |
| Журнал действий (системные журналы) | **нет** | да |
| Учётные записи | **нет** | да |
| Переключение версии классификатора | **нет** | да |

Преподавателю журнал действий не даём намеренно: ТЗ относит
«просматривать системные журналы» к функциям мониторинга
администратора, а для разбора занятия у преподавателя есть свой
инструмент — отчёты. Кто когда входил и с какого адреса, ему знать
незачем.

Зато последствия смены версии классификатора преподаватель видит:
это не конфигурация системы, а переаттестация — какие сценарии
перестали соответствовать эталону и кому из курсантов новые позиции
не попадались.

## Аудит

Раздел «Аудит» инструкции требует, чтобы было видно, кто, что и когда
сделал. Пишутся: вход и неудачная попытка входа с причиной, начало
занятия, сохранение карточки (с номером, классом, списком служб,
временем и баллом), проставленный статус реагирования, заказ отчёта,
заведение и отключение учётной записи, смена активной версии
классификатора и автоматические переходы статуса карточки.

Адрес клиента берётся из `X-Forwarded-For` (за обратным прокси) или
из самого соединения. Верить заголовку можно потому, что по ТЗ система
работает в изолированном контуре; в открытой сети его пришлось бы
перезаписывать на прокси.

Пароли в журнал не попадают — на это есть отдельный тест.

Таблица партиционирована по месяцам под требование «хранить не менее
6 месяцев». Партиции на ближайшие четыре месяца создаёт `jobs::maintenance`
раз в сутки: миграция завела их только до декабря 2026, и без этой
задачи запись в журнал однажды упала бы вместе с действием, которое
её вызвала.

## Резервное копирование

`BACKUP_DIR` не задан — копии не делаются. Задан — раз в сутки
`pg_dump --format=custom`, копии старше `BACKUP_KEEP_DAYS` (по ТЗ 30)
удаляются. Сжатый custom-дамп восстанавливается выборочно и занимает
вчетверо меньше обычного SQL.

## Канал класса

`GET /ws?token=<JWT>` — тот же токен, что и в REST, только в query:
заголовок Authorization браузерный WebSocket-клиент выставить не умеет.

Шина — один широковещательный канал на процесс, фильтрация на стороне
подписчика (`ws/hub.rs`). Карта «топик → канал» была бы лишней:
аудитория стенда это учебный класс, а карту пришлось бы чистить от
пустых топиков и сторожить гонки между подпиской и отправкой. Если
стендов станет много, это место меняется на Redis pub/sub, наружу
торчат только `publish` и `subscribe`.

Топики: `service:<id>`, `session:<uuid>`, `group:<uuid>`, `user:<uuid>`.
**Подписка проверяется теми же правилами, что и REST** — иначе канал
стал бы дырой в обход разграничения: подписался на чужой топик и
читаешь чужую ленту.

События: `card.dispatched`, `response.recorded`, `ack.timeout`,
`card.status`, `session.started`, `session.finished`. Плюс служебные
`subscribed`, `error`, `pong` и `lagged` — последнее сервер шлёт, когда
клиент отстал и часть событий потеряна, чтобы тот перечитал состояние
через REST, а не показывал устаревший журнал.

Канал — ускорение, а не источник истины: фронтенд по событию всегда
перечитывает данные через REST.

## Отчёты

`GET /api/reports/session/:id?format=json|csv` — пять блоков, которые
перечисляет ТЗ: действия обучающегося, замечания, время заполнения,
отличие от норматива и результат проверки грамматики.

CSV собирается под Excel на русской локали: разделитель — точка с
запятой, в начале файла BOM, переводы строк CRLF. С запятой Excel
сваливает строку в одну ячейку, без BOM показывает «Ð¿Ð¾».

`POST /api/reports/group/:id` и `POST /api/insights/group/:id` ставят
задачу в очередь. Числа в сводке считает SQL, модель только формулирует
текст по готовой статистике — выдумать процент она не может.

## Модели

Ни один эндпоинт не зависит от модели напрямую — только от трейтов
в `ml/mod.rs`. Провайдер выбирается переменной:

```
ML_PROVIDER=mock   работает сейчас, система функциональна без моделей
ML_PROVIDER=onnx   появится в задаче про ONNX
ML_PROVIDER=http   внешний сервис моделей
```

Заглушки детерминированные: одинаковый вход даёт одинаковый выход,
иначе тесты плавают. Отдельно отмечу `MockLlm::group_insights` — он
**не выдумывает цифры**, а пересказывает настоящую агрегацию. Демо
выглядит честно, и при замене на модель контракт не меняется.

## Миграции

Имя файла: `<timestamp>_<описание>.sql`, где timestamp — **сплошное
число без разделителей**, например `20260920210003_scenarios.sql`.

Это не стиль, а требование sqlx: версией считается всё до первого `_`.
Если написать `20260920_2100_scenarios.sql`, версией станет `20260920`,
и все миграции получат одинаковый номер.

Чужие миграции **никогда не редактируем и не переименовываем** — только
добавляем свою следующую. Так двое разработчиков физически не столкнутся
в одном файле.

Накатить на чистую базу заново:

```bash
docker exec arm112-db psql -U arm112 -d arm112 \
  -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"
cargo run
```

## Добавление своего роутера

В `api/mod.rs` добавьте строку **в конец** списка `.merge(...)`,
соседние не переставляйте. Git сливает добавления в разные места
без конфликта, а перестановки — нет.

```rust
.merge(health::routes())
.merge(auth::routes())   // ← ваша строка здесь
```
