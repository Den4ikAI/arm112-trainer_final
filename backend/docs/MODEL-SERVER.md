# Сервер языковой модели

Нужен только для подготовки и правки учебных вызовов. Всё остальное —
подбор служб, оценка, статусы — считается без моделей, и система
полностью работоспособна с `ML_PROVIDER=mock`.

## Что используется

**GigaChat 3.1 10B-A1.8B**, лицензия MIT. Смесь экспертов: 10 млрд
параметров всего, 1,8 млрд активных. На процессоре скорость определяют
активные, поэтому она обгоняет плотные модели вчетверо меньшего
размера.

Замеры на профиле стенда — шесть потоков, только CPU, Q4_K_M:

| | Разбор запроса | Генерация |
|---|---|---|
| Qwen3.5 4B (плотная) | 51 ток/с | 11 ток/с |
| LFM2.5 8B (MoE) | 97 ток/с | 31 ток/с |
| GigaChat 3.1 (MoE) | 42–46 ток/с | 10,3 ток/с |
| **GigaChat 3.1 + MTP** | 42–46 ток/с | **14,8 ток/с** |

LFM2.5 быстрее, но на русском заметно слабее — проверяли.

## Ускорение на MTP

Модель обучена с Multi-Token Prediction: в весах есть голова,
предсказывающая следующий токен. Она работает как черновик для
спекулятивного декодирования — своя же, без отдельной модели.

**Даёт +44%.** Ключевой параметр — `--spec-draft-n-max 1`.
По умолчанию llama.cpp предлагает три токена; при здешнем качестве
головы принимается в среднем 1,7, и лишние проверки съедают весь
выигрыш — с ними MTP медленнее, чем без него.

| Длина догадки | Приём | Генерация |
|---|---|---|
| 3 (по умолчанию) | 26–33% | 9,3 ток/с |
| **1** | **73%** | **14,8 ток/с** |

## Как собрана модель

В опубликованном GGUF (`ai-sage/GigaChat3.1-10B-A1.8B-GGUF`) блока MTP
нет — 414 тензоров, ни одного `nextn`. Нужна своя конвертация из
исходных весов, и для неё — две правки llama.cpp:

**`docs/mtp-1-converter.patch`** — экспорт блока NextN для
`DeepseekV3ForCausalLM`. Машинерия в llama.cpp была написана, но
включена только для DeepSeek V3.2.

**`docs/mtp-2-runtime.patch`** — `graph_mtp` в `src/models/deepseek2.cpp`
безусловно требовал сжатия Q через LoRA. У GigaChat `q_lora_rank`
не задан, используется полная матрица `wq`. Основной граф это
различает, MTP-граф — нет.

Обе правки общие: первая чинит любую модель семейства DeepSeek V3
с головой MTP, вторая — любую без Q-LoRA.

```bash
python convert_hf_to_gguf.py <исходные веса> --outtype bf16 --outfile full-mtp-bf16.gguf
llama-quantize full-mtp-bf16.gguf full-mtp-q4_K_M.gguf Q4_K_M 24
```

Конвертация требует `transformers` не ниже 5.x: более старые не читают
токенизатор GigaChat. При этом `transformers` 5.x строго проверяет типы
и падает на `routed_scaling_factor: 1` целым вместо дробного — в
`config.json` исходной модели это надо поправить.

## GFusion: диффузия вместо спекулятивного декодирования

`ai-sage/GFusion-10B-A1.8B` — та же база, тот же `model_type`
(`deepseek_v3`), конфиги совпадают в 35 ключах из 43. Отличие в
способе генерации: не по одному токену, а блоками по 32 позиции,
которые уточняются итеративно. На процессоре это выглядело
перспективным: проход по 32 позициям стоит 468 мс против 35 мс за
проход по одной, то есть дороже в 13 раз, а не в 32, — чтение весов
размазывается по всем позициям блока.

Замер показал, что модель этой параллельностью не пользуется:

| бюджет энтропии | шагов на блок | токенов за проход |
|---|---|---|
| 0,15 (по умолчанию) | 21 | 1,29 |
| 0,4 | 20 | 1,35 |
| 0,8 | 19 | 1,42 |
| наш MTP | — | **1,73** |

Блок из 32 токенов сходится за двадцать уточнений, а не за три, как
требовалось бы для выигрыша. Пересчёт на шесть потоков и q4_K_M даёт
3,1–3,4 ток/с против наших 14,8.

Скрипт замера — `измерить-gfusion.py` рядом с этим файлом. Он требует
`transformers==4.53.2`: на 5.x эксперты MoE молча не загружаются
(там ждут слитые `gate_up_proj`), и модель считает на случайных весах.

Отдельно: llama-server диффузию не умеет вовсе, она живёт в
`examples/diffusion`, и `GFusionForDiffusionLM` там не зарегистрирован.
Переход стоил бы нам совместимого с OpenAI эндпоинта, а с ним —
ограничения ответа схемой JSON.

## Что проверялось и не дало эффекта

* **Температура** — приём догадок одинаков при 0,0 / 0,3 / 0,7.
* **Голова в F16 вместо Q4** — приём тот же, а работает медленнее:
  больший блок дороже прогонять. Дело не в квантовании.
