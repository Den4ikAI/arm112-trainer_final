# Сборка под Windows

Проверено 21.09.2026 (после добавления JWT и argon2). Работает.

## Как собрать

```bash
docker build -f Dockerfile.windows -t arm112-winbuild .
mkdir -p out
docker run --rm -v "$PWD/out:/out" arm112-winbuild
# → out/arm112.exe
```

Первая сборка образа занимает несколько минут (тянется `rust:1-bookworm`
и `mingw-w64`, образ ~3,8 ГБ). Дальше сборка exe — около 30 секунд.

## Результат

```
out/arm112.exe: PE32+ executable (console) x86-64, for MS Windows
19 МБ (release)
```

Для сравнения, тот же бинарник под Linux — 7,9 МБ.

Вырос с 14 МБ: добавились argon2 и jsonwebtoken. Последний собирается
с `default-features = false, features = ["rust_crypto"]` — чистый Rust
вместо aws-lc-rs, которому нужен сишный тулчейн. Иначе линковка под
mingw не проходит.

## Почему через Docker, а не напрямую

Для цели `x86_64-pc-windows-gnu` нужен линковщик `x86_64-w64-mingw32-gcc`.
В системе его нет, а установка требует root. Docker решает это без правки
хостовой машины и заодно делает сборку воспроизводимой — важно, потому что
по ТЗ нужны «подробные инструкции по компиляции, сборке и установке».

Если у вас mingw уже стоит, можно и напрямую:

```bash
rustup target add x86_64-pc-windows-gnu
cargo build --release --target x86_64-pc-windows-gnu
```

## ONNX Runtime: проверено отдельно

Главный риск был в том, что `ort` не соберётся под Windows — ведь ради
локального инференса без Python всё и затевалось. Проверено в том же
образе: **собирается**.

Но есть нюанс с фичами.

### Что не работает

```toml
ort = { features = ["download-binaries"] }           # ошибка: нужна TLS-фича
ort = { features = ["download-binaries", "tls-rustls"] }  # тянет openssl-sys
```

Вариант с `tls-rustls` подтягивает `openssl-sys`, которому нужен системный
OpenSSL и `pkg-config`. На чистой машине не собирается, а для кросс-сборки
это лишняя зависимость от хоста.

### Что работает и что берём

```toml
ort = { version = "2.0.0-rc.13", default-features = false,
        features = ["load-dynamic", "ndarray"] }
```

`load-dynamic` означает, что библиотека ONNX Runtime **не вкомпилируется
в бинарник, а загрузится в рантайме** из файла рядом с ним. Это ровно то,
что нужно для доставки папкой:

```
arm112.exe
onnxruntime.dll
models/
  gigaam.onnx
  piper-ru.onnx
  rubert-nli.onnx
```

Плюс к тому, `download-binaries` качает рантайм во время сборки — то есть
требует интернет на машине сборки. Для изолированного контура это
неприемлемо в принципе, так что `load-dynamic` — не обходной путь,
а правильный выбор.

## Честная оговорка про «один бинарник»

Одного файла не получится: рядом с exe поедут `onnxruntime.dll`
и каталог моделей (GigaAM ~250 МБ, голос Piper ~60 МБ, rubert ~45 МБ).

Но это по-прежнему несопоставимо проще, чем Python с venv, колёсами
и CUDA. Инструкция по установке сводится к «распакуйте архив и запустите
exe», а не к странице команд.

## Что ещё не проверено

* Сам exe **не запускался под Windows** — проверена только сборка.
  Стоит прогнать на живой машине до сдачи.
* Загрузка `onnxruntime.dll` в рантайме не проверена: на момент проверки
  `ort` подключался пустым, без реального инференса.
* Цель `x86_64-pc-windows-msvc` не проверялась. Она требует MSVC-линковщик
  и `cargo-xwin`; `gnu` для наших задач достаточно.
