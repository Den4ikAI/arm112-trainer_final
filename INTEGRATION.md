# Встраивание в стороннюю систему

По ТЗ решение должно быть отдельным сервисом, который может стать
независимой информационной системой или её компонентом. Здесь — что
для этого нужно знать.

## Машиночитаемое описание

```
GET /api/openapi.json     схема OpenAPI 3.1
GET /api/docs             Swagger UI
```

Схема собирается из самих обработчиков, а не пишется отдельно:
отдельная разошлась бы с кодом на первой правке и стала бы хуже, чем
её отсутствие — интегратор доверял бы описанию, которое врёт.
За этим следит тест `backend/tests/openapi.rs`: забытая аннотация на
новом маршруте роняет сборку.

Сгенерировать клиент можно любым стандартным генератором:

```bash
curl -o openapi.json http://<адрес>/api/openapi.json
openapi-generator-cli generate -i openapi.json -g python -o ./client
```

## Аутентификация

```http
POST /api/auth/login
{ "login": "operator1", "password": "...", "workstation": "4" }
→ 200 { "token": "eyJ...", "user": { "id", "role", "serviceId", ... } }
```

Дальше токен идёт заголовком:

```
Authorization: Bearer eyJ...
```

Срок жизни — 8 часов (`JWT_TTL_HOURS`). Серверного списка отзыва нет:
для изолированного учебного контура это лишняя сложность. Протухший
токен даёт `401`, и клиент должен получить новый.

Тот же токен открывает канал событий, но в query — заголовок там
выставить нельзя, это ограничение браузерного WebSocket:

```
GET /ws?token=eyJ...
```

## Разграничение доступа

Роль и служба — **независимые оси**. Роль говорит, что человек умеет
делать; служба (`serviceId`) — какие карточки он видит. ДДС это
организация, а не человек.

| Роль | Что доступно |
|---|---|
| `student` | свои занятия, лента своей службы, статусы за свою службу |
| `teacher` | всё выше плюс любые занятия, журнал действий, отчёты по группам |
| `admin` | всё выше плюс учётные записи и переключение версии классификатора |

Правила проверяются на сервере, а не в интерфейсе. Это же касается
канала событий: подписка на чужой топик отклоняется — иначе канал
обошёл бы всё разграничение.

## Основные сценарии вызова

### Подобрать службы по признакам происшествия

Не требует ни занятия, ни карточки — чистая функция от признаков.
Самый вероятный способ встраивания: своя система заполняет карточку,
а список оповещения берёт отсюда.

```http
POST /api/classifier/evaluate
{
  "typeIds": ["101"],
  "answers": {
    "where": ["Дом"],
    "fire-sign": ["Открытое пламя / Дым"],
    "house-kind": ["Дом частный"],
    "inhouse": ["Крыша"]
  }
}
→ 200 {
  "outcome": "пожар: частный дом",
  "positions": ["1050901", "1050902"],
  "services": [ { "serviceId": "mchs", "title": "...", "responding": true } ],
  "informational": [ ... ],
  "reason": null
}
```

`services` — те, кто реагирует. `informational` — те, кому уходит
копия. Различать обязательно: за информационные копии нельзя
штрафовать и нельзя ждать от них выезда.

Если признаков не хватает, `outcome` пустой, а `reason` объясняет,
чего именно недостаёт. Движок не выдумывает позицию.

### Провести занятие целиком

```http
POST   /api/sessions                  { scenarioId, mode }
POST   /api/sessions/{id}/ask         { factId }      → ответ заявителя
PATCH  /api/sessions/{id}/card        частичное обновление
POST   /api/sessions/{id}/save                        → разбор
GET    /api/sessions/{id}/grade                       → он же потом
```

`PATCH` частичный: `address` и `answers` сливаются по полям на стороне
сервера. Клиент шлёт только изменившееся.

Эталон и ответы на не заданные вопросы наружу не отдаются ни на одном
шаге. Иначе метрику «выяснил или угадал» можно обойти, посмотрев
ответ в отладчике браузера.

### Получить отчёт

```http
GET  /api/reports/session/{id}              → JSON
GET  /api/reports/session/{id}?format=csv   → выгрузка для Excel
POST /api/reports/group/{id}                → 202 { jobId }
GET  /api/jobs/{jobId}                      → состояние и результат
```

Отчёт по группе считается в очереди: норматив ТЗ на подготовку —
30 секунд, и держать соединение всё это время незачем.

CSV собран под Excel на русской локали: разделитель — точка с запятой,
в начале файла BOM, переводы строк CRLF.

## Канал событий

```
GET /ws?token=<JWT>

клиент → { "type": "subscribe", "topics": ["service:mchs"] }
сервер → { "type": "card.dispatched", "cardId": "...", "number": "...", ... }
```

Топики: `service:<id>`, `session:<uuid>`, `group:<uuid>`, `user:<uuid>`.

События: `card.dispatched`, `response.recorded`, `ack.timeout`,
`card.status`, `session.started`, `session.finished`.

Канал — **ускорение, а не источник истины**. По событию всегда
перечитывайте данные через REST: после разрыва соединения часть
событий теряется, и сервер честно сообщает об этом отдельным
сообщением `lagged`.

## Коды ошибок

Тело ответа всегда содержит поле `error` с машинным кодом.

| Код | HTTP | Когда |
|---|---|---|
| `validation_error` | 400 | не прошли проверку данные запроса |
| `unauthorized` | 401 | нет токена или он протух |
| `forbidden` | 403 | роль не позволяет |
| `not_found` | 404 | нет объекта либо он не виден этой роли |
| `conflict` | 409 | состояние не допускает действие |
| `comment_required` | 422 | статус требует комментария |
| `status_not_allowed` | 422 | статус нельзя выбрать сейчас; в ответе поле `allowed` |
| `auto_service_removal` | 422 | нельзя снять службу, подобранную классификатором |

`404` вместо `403` для чужих занятий и карточек — намеренно: по коду
ответа не должно быть видно, что объект вообще существует.

## Смена версии классификатора

Классификатор живой: между двумя версиями из материалов задачи
появились восемь служб и позиция «БПЛА». По нему считается и список
оповещения, и эталон при разборе, поэтому подменять его молча нельзя.

```http
GET  /api/classifier/versions/{a}/diff/{b}   что изменилось
GET  /api/classifier/versions/{id}/impact    кого это заденет
POST /api/admin/classifier-versions/{id}/activate
```

`impact` считается **до** переключения и показывает, какие сценарии
перестали соответствовать эталону и какие новые позиции никто
не отрабатывал. Уже выставленные оценки не пересчитываются: они
зафиксировали тот справочник, что действовал в момент сохранения.

## Развёртывание

Сервер — один исполняемый файл, зависимость только PostgreSQL 16.
Миграции накатываются при старте. Сборка под Windows описана
в `backend/CROSS-BUILD.md`.

```
DATABASE_URL     обязателен
BIND_ADDR        по умолчанию 127.0.0.1:8080
JWT_SECRET       в проде — длинная случайная строка
JWT_TTL_HOURS    по умолчанию 8
ML_PROVIDER      mock (система работает без моделей)
BACKUP_DIR       не задан — резервные копии не делаются
BACKUP_KEEP_DAYS по умолчанию 30
```
